## 1. 요약

**확인하려던 것.** 같은 반도체 업종인 두 회사 선물의 1분 단위 상대가격이 평소 관계에서 크게 벗어났을 때 **되돌아오는가**, 그리고 그 되돌림이 **두 다리 × 진입·청산 네 번의 거래 비용을 넘는가**. 동시에 이번 주 과제의 핵심인 **두 주문을 하나의 거래로 관리**(한쪽만 체결되는 상황 처리)를 실제 모의계좌에서 검증합니다.

**한 것.**
1. 실행 **전에** 9거래일 1분봉으로 유동성·관계·괴리 빈도·비용을 재고, 설계용 5일 / 검증용 4일로 나눠 규칙을 정한 뒤 바꾸지 않기로 했습니다(3-7절).
2. 두 다리 주문을 상태로 관리하는 실행 코드를 작성하고, 가짜 서버로 「둘째 다리 미체결·부분체결·첫 다리 거부·취소 직전 체결·나뉜 체결·응답 시간 초과·토큰 거절·실시간 끊김」을 일부러 만들어 시험했습니다.
3. 운영진 안내에 따라 시세를 **REST → WebSocket** 구조로 바꿨습니다(4절).

**지금까지 알게 된 것(11/10 기준).**
- **과거 24거래일 워크포워드 검증(3-8절):** 판정 봉 종가에 바로 체결된다고 보면 비용 0·0.5틱에서 하루 평균 손익의 95% 구간이 0 보다 위이고 손익분기는 다리마다 약 1틱. **그러나 체결을 1분만 늦추면 비용 0 에서도 이익이 사라집니다**(하루 평균 +1.5만원, 95% 구간 −8.4만~+11.3만). → **되돌림은 있지만 대부분 1분 안에 끝나거나 호가 튕김(bid-ask bounce)에 가까워, 1분봉 판단·시장가 주문으로는 잡을 수 없음(H1 은 조건부, H2 는 아니오)**.
- 괴리는 하루 약 10번 나고 대부분(86~97%) 손절선 전에 되돌아오지만, 되돌아온 폭(약 21bp)이 왕복 비용(약 21bp)과 거의 같습니다 — **2주차에 이어 비용이 결과를 정하는 구조**.
- 11/10 첫 실거래에서 **판정 가격으로는 +5만원**이었던 거래가 **체결 비용 9만원** 때문에 −4만원이 됐습니다. 괴리가 몇 초 만에 풀렸는데 주문이 봉 마감 7초 뒤에 나간 것이 주원인 → 판정 지연을 2초로 줄이고 실시간 시세로 바꿨습니다.
- 두 다리 주문은 모의계좌에서 **한쪽만 체결된 시간 0.64~0.67초**로 맞춰졌습니다(REST 체결 확인 기준).

### 3-2. 왜 이 페어인가

| 후보 | 판단 |
| --- | --- |
| **삼성전자–SK하이닉스 주식선물 (채택)** | 두 레그 주문 관리라는 과제 핵심을 그대로 다루고, 반도체라 팀 탐구 주제(수출 산업)와 이어짐. 두 종목 모두 주식선물 중 유동성이 높은 편. 선물이라 매도 다리를 공매도 제약 없이 잡을 수 있음 |
| 미니코스피200–코스피200 | 같은 지수라 수렴 근거는 가장 확실하나 가격 차가 거의 늘 1~2틱 안이라 기회가 드묾 |
| 삼성 11월–12월물 캘린더 | 보유비용이라는 기준가가 있으나 11월물 만기(11/12)로 실행 가능일이 하루뿐 |
| SGX 원달러–국내 미국달러 | 국내·해외 두 계좌와 시간대를 함께 다뤄야 해 이번 주 일정에 무거움 |

**실제로 괴리가 커졌던 때.** 2024-05-24 삼성 HBM 엔비디아 테스트 관련 보도(삼성 −3.1% · 하이닉스 −0.7%), 2026-08-06 솔리다임 상장설(하이닉스 하루 −10.37%), 2026-09-21~10-21 같은 하락장에서 삼성 −14.4% · 하이닉스 −30.3%(외국인 하이닉스 18거래일 연속 순매도). **큰 괴리는 대부분 회사 고유 뉴스라 잘 되돌아오지 않습니다.** 이 전략이 노리는 것은 장중 몇 분~수십 분 안에 풀리는 작은 쏠림이고, 큰 괴리는 손절 규칙으로 막아야 하는 위험입니다.

### 3-3. 매매 규칙

| 구분 | 조건 |
| --- | --- |
| 스프레드 | s = ln(삼성) − β·ln(하이닉스), **β = 0.59** (실행 전 9일 1분 수익률 회귀, 고정) |
| z | (s − 최근 40봉 평균) ÷ 최근 40봉 표준편차 — 하루 안에서만(09:00 봉부터) |
| 진입 | z 가 +2 를 위로 넘는 봉 → **스프레드 매도**(삼성 매도 10 · 하이닉스 매수 1) / −2 를 아래로 → **스프레드 매수**(반대) |
| 진입 조건 | 그 분에 **두 종목 모두 체결**이 있었을 것(한쪽 가격이 멈춰 생긴 가짜 괴리 방지) · 진입 09:10~15:00 · 손절 뒤 3봉 대기 · 하루 20회 · 남은 손실한도 ≥ 1회 손절액 |
| 수렴 청산 | \|z\| ≤ 0.5 |
| 손절 | z 가 진입 방향으로 ±3.5 (봉 마감) **또는** 두 다리 합산 평가손실 ≥ 15만원 (실시간 체결가로 수시) |
| 시간 청산 | 보유 60봉 |
| 장 마감 | 15:15 전량 정리 (현물 15:30 마감 전) |
| 주문 | 시장가 FAS. 하이닉스(1계약) 먼저 → 체결 확인 → 삼성(10계약) |
| 일일 손실 한도 | 50만원 — 남은 한도가 1회 손절액(15만원)보다 작으면 신규 진입 중지 |

### 3-4. 값마다 그렇게 정한 이유

| 규칙 | 값 | 이유 |
| --- | --- | --- |
| 로그 가격·수익률 β | 0.59 | 두 종목은 가격 수준·변동성이 크게 달라 가격 수준 회귀는 며칠 추세만으로 그럴듯한 β 가 나옴(가짜 회귀). 수익률 β 는 「하이닉스 1% → 삼성 0.59%」로 해석이 쉽고, 계약 수는 명목금액으로 맞춤 |
| rolling 40봉 z | 40 | 고정 평균(fixed)은 날마다 스프레드 수준이 옮겨 가 하루 0.6번만 신호, 반감기 372분 → 쓸 수 없음(3-7절). **최적화하지 않은 출발값** |
| 진입 2.0 / 청산 0.5 / 손절 3.5 | — | 표준적인 출발값. 진입 2.5·청산 0·창 60 등 6개 조합을 비교했으나 검증 구간에서 모두 본전 수준이라 바꿀 근거가 없음 |
| 바로 진입 | immediate | 「이탈 뒤 복귀 확인」(reentry)은 먹을 폭이 절반(약 11bp)으로 줄어 비용을 더 못 넘음(3-7절) — 2주차와 반대 결론 |
| 함께 체결된 봉만 | — | 주식선물은 현물보다 거래가 얇아 한쪽만 체결된 분이 14%. 그 분의 괴리는 가짜일 수 있음 |
| 10 : 1 | — | 0.59 × 삼성 명목(약 2,000만원) ≈ 하이닉스 명목(약 1,190만원). 39 : 4 가 오차는 더 작지만 금액이 너무 큼 |
| 하이닉스 먼저 | — | 1계약이라 체결이 덜 확실한 쪽을 먼저 확인해야, 실패 시 되돌릴 것이 적음 |
| 금액 손절 15만원 | — | 실행 전 9일 rolling σ 중앙값 18bp → 진입(2σ)에서 z 손절(3.5σ)까지 약 27bp ≈ 5만원. 급변 시 z 판정(봉 마감)보다 먼저 막는 상한 |

### 3-5. 미리 알고 있는 약점

- **회사 고유 뉴스**(HBM 수주·자회사 상장 등)로 괴리가 계속 벌어지면 수렴하지 않고 손절됨.
- **rolling 평균의 「따라오는 수렴」**: 가격 관계가 돌아오지 않아도 평균이 따라와 z 가 0.5 안에 들면 청산 → 「수렴 청산인데 손실」이 생김(2주차 중심선 청산과 같은 성질, 11/10 첫 거래).
- **비용**: 시장가 4번 = 다리마다 약 1틱. 실행 전 분석에서 수렴 폭 ≈ 비용.
- **판정과 주문 사이의 지연**: 1분봉 마감 뒤 주문하므로 몇 초 사이 풀리는 괴리는 놓침.
- **한쪽만 체결**: 두 주문은 원자적으로 함께 체결되지 않음 → 5절의 상태 관리로 대응.

## 4. 사용 API와 프로그램 구조

### 4-1. 구조 — 처음은 REST, 이후는 WebSocket

```
[시작·REST]  토큰 → 현재가(종목 확인) → 주문가능수량 → 잔고 → 오늘 분봉(지표 준비)
[실시간·WS]  접속키 → wss 연결 → 세션 초기화 → 구독: KA(삼성) · KA(하이닉스) · O1(주문/체결)
                │ 체결마다: 최신가 갱신(금액 손절 0.2초마다) · 거래소 체결시각의 분으로 1분봉 누적
                ▼
           pair_engine (봉 마감 2초 뒤 판정) ── PairIntent ──► pair_broker
                                                          REST 주문 → O1 통보로 체결 확인(늦으면 주문내역 조회)
                                                          → 두 종목 잔고 대조(REST) → 어긋나면 잔고 기준 정리
[대체]  실시간 끊김 → 현재가 REST(--poll 초) · 끊긴 분의 봉은 REST 분봉으로 보충 · 1·2·5·10·30초 간격 재연결
journal ──► results/<run_id>/ (events · bars · signals · pair_legs · pairs · trades · ticks · ws_orders · api_calls · summary)
```

### 4-3. 두 다리 주문 처리 (`pair_broker.py`)

| 상황 | 처리 | 결과 |
| --- | --- | --- |
| 두 다리 체결 | 하이닉스 → 체결 확인 → 삼성 → 체결 확인 | `COMPLETE` |
| 첫 다리 미체결·거부 | 남은 수량 취소 → 최종 확인 | `ABORTED` (노출 없음) |
| 둘째 다리 일부만 | 앞 주문이 최종 상태일 때만 남은 수량 1번 더 → 그래도 모자라면 체결된 다리를 반대로 되돌림 | `UNWOUND` / 못 되돌리면 `BROKEN` |
| 청산 미완료 | 남은 수량 최대 3번 더 | `COMPLETE` / `BROKEN` |
| 응답 없음 | **다시 보내지 않고** 주문내역에서 찾음. 못 찾으면 그 다리는 `UNKNOWN`(재전송 금지) | 잔고 대조로 판정 |
| 취소 직전 체결 | 취소 뒤 주문내역을 다시 읽어 최종 체결수량을 씀 | — |
| 잔고 불일치·`BROKEN` | 잔고 기준으로 시장가 정리 → 엔진 무포지션 → 신규 진입 중지 | — |

페어 ID 하나에 두 주문번호·체결수량·체결가·판정가 대비 미끄러짐·**한쪽만 체결된 시간(ms)**·체결 확인 경로(ws/rest)를 묶어 기록합니다.

### 4-4. API 를 쓸 때 지킨 것
- 성공 판정: HTTP 200 이어도 `errorCode`(정상코드 제외)·`msg_cd` 가 있으면 실패.
- 토큰 거절(401·EGW05x·**EGW023**): 같은 토큰으로 0.4초 뒤 다시 → 그래도 안 되면 재발급(10초에 한 번까지) → 한 번 더. 게이트웨이의 처리 전 거절이라 주문도 중복되지 않음(8-1절).
- 주문은 자동 재전송하지 않음. 분봉은 연속조회 키 대신 시각 창 둘(오전·오후)로 나눠 받음(공개 저장소 메모: 이어받기 키 신뢰 불가).
- 실시간: 웹소켓 규격 ping 프레임은 끔(켜면 국내 연결이 끊김), 서버 `pingpong` 은 받은 그대로 되돌림, 접속키는 연결마다 새로.
- 밀린 봉(마감 뒤 1봉+30초 초과)은 지표만 갱신하고 주문하지 않음(2주차 10/29 교훈).

### 4-5. 참고한 것
API 경로·필드·실시간 절차는 [PetterChanHyuk/nh-futures-open-api](https://github.com/PetterChanHyuk/nh-futures-open-api) 의 `catalog.py`·`domestic_futureoption_functions.py`·`realtime/link.py` 와 응답 기록(`tests/fixtures/nh/`)에서 확인했고, 코드는 그 명세에 맞춰 새로 작성했습니다. 2주차 `nh_client.py` 를 이어 썼습니다.
